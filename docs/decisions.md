# Technical decisions

Product decisions not covered by the plan are listed under "Open questions" for the owner.

## Architecture

- **Tool layer is the only write path for agents and staff screens** (`callTool` in `packages/core/src/tools/registry.ts`). It validates, checks the actor's allow-list (`staff:doctor`, `agent:queue`, `patient`, `system`...), checks the clinic's module switch, runs in a clinic-scoped transaction, writes `agent_actions`, and publishes live events only after commit. Failed and denied calls are audited too.
- **Row-level security via a session setting.** Each transaction does `set_config('app.clinic_id', ..., true)`; policies compare `clinic_id` to it. The app role is non-superuser and policies are `FORCE`d, so a missing context returns zero rows (fails closed). Staff login uses a small `SECURITY DEFINER` function because no clinic is known yet. Background workers list work with `SECURITY DEFINER` functions that return ids only (`due_followups`, `clinics_for_sweeps`) and then act inside each clinic's scope.
- **Audit log is append-only** for the app role (UPDATE/DELETE revoked).
- **Orchestrator pipeline order:** store message, human-owned? stop, red-flag check, human handoff/upset, medical question, queue-jump refusal, continue active flow, route by intent. Any exception sends a safe fallback reply and flags the receptionist (never silence).
- **LLM is optional.** Booking, queue, intake, check-in and the running-late flow are deterministic state machines; the LLM is used for the second red-flag layer, free-form clinic questions (tool loop restricted to `get_clinic_info`, `list_free_slots`, `flag_to_receptionist`), intake summaries and unusual "running late" phrasing. All LLM text passes a medical-policy output filter. `LlmGate` marks the model down after 2 consecutive failures for 30s and emits `llm_status`.
- **Mock WhatsApp:** the stored `messages` row is the delivery; the simulator page reads it and refreshes on WebSocket events. A real vendor adapter implements `MessagingChannel.send`. Sending happens inside the tool transaction for now; a real adapter should switch to an outbox + job so a vendor call never holds a DB transaction.
- **Events:** Redis pub/sub when reachable, otherwise in-process. Public screens (TV, simulator) get only `queue_changed` / `conversation_updated` (no data); staff sockets get everything for their clinic.
- **Auth:** scrypt password hashes, JWT bearer (12h) held in browser storage. For a real deployment move to httpOnly cookies and add rate limiting on public endpoints; noted, not done in M0-M3.
- **Jobs:** pg-boss (own `pgboss` schema, admin connection) runs `followups.sweep` and `queue.sweep` every minute and `recall.sweep` daily. Disable with `JOBS_ENABLED=false` (tests/e2e do).
- **Next.js 14, plain CSS, no UI kit:** keeps the screens easy to read and change.
- **Playwright uses installed Google Chrome** (`channel: 'chrome'`), so no browser download.

## Post-pilot features (started after go-ahead)

- **Live channels.** AI-Agent-Platform will own WhatsApp delivery and telephone connections. Sahayak retains vendor-neutral adapters, the outbox, and local simulators. Platform channel execution is pending integration.
- **Voice.** Mock speech adapters and `/voice/:slug/turn` remain for simulator testing. Doctor voice notes use `/staff/schedule/propose-voice` with confirmation. Live phone calls await AI-Agent-Platform integration.
- **Agent builder.** Doctor-only settings screen (`/doctor/settings`) and `update_clinic_settings` tool: clinic info, timings, consult length, intake questions (EN+HI), FAQs (keyword to answer, EN+HI, held to the no-medical-advice policy), follow-up timings, per-agent on/off, extra emergency phrases. Switching an agent off hands its chats to the receptionist. Emergency detection and the fixed safety replies are not configurable. Every change is stored in append-only `settings_changes`. Doctor FAQs win over built-in info replies.

- **Conversational booking with no human.** A patient says "I need an appointment"; the agent asks which day and time (or takes it from the first message: "tomorrow evening", "Friday after 4", "kal subah", "शुक्रवार 4 बजे के बाद", "5 Oct", "earliest"), searches the doctor's existing appointments for free slots in that window, offers up to 3, and books on a number reply (or YES for a single option). If nothing is free then, it says so and offers the nearest. "Friday instead" restarts the search; two unclear answers fall back to the earliest slots. Moving and cancelling work the same way. Unknown numbers first give a name and consent (their requested time is remembered). The deterministic parser means this works without the LLM. Each doctor can have their own WhatsApp number (`doctors.whatsapp_number`, set on the agent-builder screen); a message to it books with that doctor and never asks which. The doctor's screen refreshes live on every booking, move or cancel. Not yet: reminder consent at booking time (only visit-data consent is asked from new numbers, so reminders are sent only to patients who consented at check-in), and "can I speak to the doctor" requests, which still go to the receptionist as a handoff.

## Priority features (reminder consent, DPDP, safety report, integrations, setup)

- **Reminder consent at booking.** After a WhatsApp booking, a patient without reminder consent is asked once (YES/NO). YES records both messaging and reminder consent and schedules the reminder; anything else drops the question.
- **DPDP.** Patients can ask on WhatsApp for their data ("my data"), erase it ("delete my data", then DELETE to confirm) or stop messages (STOP; START to resume); the desk can export/erase from Privacy requests. Erasure removes name, phone, birth year, chats, intake answers and follow-ups and strips personal content from the audit log; de-identified appointment and visit rows stay so the clinic's schedule and statistics remain correct. The audit table stays append-only for the app: only two vetted security-definer functions can redact (and only for the current clinic, never shorter than 365 days). Tools whose output holds personal data (exports, data summaries, API keys, webhook secrets) store a summary in the audit log instead. Retention runs nightly per clinic (defaults: chats 180 days, intake 365, audit payloads 730, inactive patients 1095, with floors). The requests log holds no personal data. Erasure also emits `patient.erased` to webhooks. Not done: a legal review of consent wording, and erasing data already copied into a clinic's other tools (the webhook is the hook for that).
- **Safety report** (`/safety`): protections checked live against the database (row-level security coverage, audit privileges), 30-day activity, the latest `pnpm eval` result (saved to `eval-results/latest.json`), and a filterable audit log with CSV export.
- **Public API and webhooks.** API keys (`shy_<prefix>_<secret>`, stored as SHA-256, shown once, scopes read < write < admin, 120 requests/min/key) go through the same tools and permission checks as the agents. Events are queued in the same transaction as the change (so they exist only if it committed), delivered with retries (8 tries over hours) and signed `t=<unix>,v1=HMAC(secret, t.body)` with a 5-minute replay window. Default payloads carry ids only; "full" adds patient name/phone and message text and is a per-webhook choice. Webhook targets must be public https URLs (private ranges refused at creation and delivery); DNS-rebinding between check and connect is not fully closed. No idempotency keys yet.
- **n8n nodes** (`packages/n8n-nodes-sahayak`): action node and an auto-registering, signature-checking trigger. Contract-tested against the real API with a stand-in for the n8n runtime; not yet run inside a live n8n.
- **Guided setup:** invite-code signup (`SIGNUP_INVITE_CODE`; off by default), seven-step wizard (clinic, hours, doctors, team, questions, try it, go live), required/optional checklist, QR poster. New staff logins get a temporary password set by the doctor (no email sending yet; there is also no password reset).

## Doctor-side features (Practo-style: ask, scribe, certificates, reputation, custom agents)

**Scope change to confirm with a lawyer:** the original brief said Sahayak runs alongside the clinic's own software and holds only contacts and queue data. With notes, uploaded reports, certificates and prescriptions Sahayak is now a system of record for clinical data. That raises the bar for privacy law (DPDP), medical-record rules, and clinical safety. Nothing here has had a legal review.

- **Ask your clinic + daily brief.** Questions map to a fixed list of read-only metrics (patients seen, no-shows with names, waits, busiest hours, cancellations, ratings...), by keyword rules in English/Hindi/Hinglish; an LLM, if present, may only pick a metric from that list, never write SQL. Doctors see their own patients unless they say "clinic"; the receptionist sees the whole clinic. A staff member's registered WhatsApp number is recognised and answered as staff (after the red-flag check). The brief goes out once a day after a configurable time, only to staff who added a number.
- **Visit-note scribe.** The doctor types or dictates (browser speech recognition in Chrome; the mock/real STT adapter exists for audio upload). The scribe only moves the doctor's own words under headings (Complaint, History, Examination, Diagnosis, Plan, Follow-up) and flags what it could not place. An optional AI arrangement is **off by default** (it would send the doctor's words, without name or number, to the hosted model) and is accepted only if >=85% of its words trace back to the transcript. Notes are drafts until the doctor signs; signed notes cannot be changed or deleted by the app (database trigger); corrections are linked amendments. Opening a record, a note or a document is audited without storing clinical text.
- **Uploads.** Patients can send photos/PDFs on WhatsApp (known numbers only); staff can upload scans. File type is judged from the file's bytes (JPEG/PNG/WebP/PDF, 8 MB), files are served as sandboxed downloads. Only doctors can open documents. Vendor media download is the channel adapter's job (the generic bridge takes base64).
- **Erasure vs medical records.** If a patient has signed notes, uploaded reports or issued documents, an erasure request deletes chats, reminders, follow-ups and consents now, keeps the clinical records, and deletes everything automatically after `clinical_years` (default 3, minimum 3) from the last clinical activity. **The 3-year default is my understanding of Indian medical-record retention, not verified.** Check the right period with your lawyer.
- **Certificates and prescriptions.** Fixed bilingual templates (sick leave, fitness, attendance); prescriptions are copied from the doctor's own list or dictated lines by a plain parser. **No AI touches a prescription**, and nothing is suggested, completed or corrected. Missing frequency/duration blocks signing. An allergy listed at intake that literally mentions a prescribed drug word raises a warning the doctor must acknowledge (cross-reactions are not claimed). Signing needs the doctor's password again and the doctor's registration number; "digital signature" here means a typed identity plus audit trail, not a legally recognised DSC. Signed documents are numbered gaplessly per year (CERT-/RX-), immutable (trigger), voidable (marked VOID, links die), sent as private 7-day links (5 downloads, only the hash stored) and verifiable by a QR code/public page that shows issuer, date and patient initials, never medical content. Hindi/English PDFs use Noto fonts; layout was checked visually on samples.
- **Reputation.** Optional private 1-5 rating asked a few hours after a visit (only patients who agreed to follow-ups; once per 60 days). **Everyone who rates is offered the public review link**: offering it only to happy patients would be review gating, which Google's policies forbid. Low ratings alert the receptionist and ask for a comment. The public clinic page (`/c/<slug>`) shows only what the clinic published; the average rating appears only if the clinic opts in and has at least 10 ratings, and counts every rating.
- **Custom agents.** A doctor describes an automation; patterns (and optionally the LLM) _propose_ a spec built only from fixed blocks (schedule or event trigger, audience filter, send-message / notify-staff / summary action). Nothing runs until a doctor reads the plain-language explanation, previews the audience and approves; any edit returns it to draft. The safety rules live in the engine, not the spec: both consents required, STOP honoured, 8:00-21:00 local only, one custom message per patient per week across all agents, 200 per run, 5 active agents, no links, no medical advice (same filter as LLM output), only {name}/{clinic} placeholders, scheduled patient messages must have an audience filter, a clinic's agents can only see that clinic. Not built: labels are set per patient by hand (no automatic diagnosis tags), no per-agent WhatsApp template approval handling (real WhatsApp needs approved templates for business-initiated messages).
- **AI-Agent-Platform authoring, phase 1.** When configured, the platform drafts a versioned custom-agent spec from the doctor's description; Sahayak validates, previews, stores a source reference, and executes its own snapshot. Existing agents keep running if the platform is down. Built-in WhatsApp and voice agent definitions are not yet authored there.
- Third-party processing note: the LLM red-flag check, free-form answers and intake summaries (and the optional scribe) send patient text to the hosted model. A data-processing agreement and a clear privacy notice to patients are needed before real use.

## Behavioural choices made while building (tell me if any is wrong)

- Queue order is arrival order across one token sequence per clinic per day. Hold keeps your place; skipped/no-show patients rejoin at the back. Only staff can hold/skip/resume; no agent tool can reorder.
- "Called" means in the room until the doctor presses "Patient is here" (`in_consultation`) or Next patient (finishes the previous one). A called patient who has not started after 8 minutes gets one nudge; after 15 minutes the token becomes a no-show and the receptionist is told.
- Estimated wait = patients ahead (including the one in the room) x the clinic's average consult minutes.
- Check-in is idempotent: a patient with an active token today gets the same token again.
- Returning-patient check: the public page learns only "returning yes/no", never a name or id.
- A new patient must consent to storing visit data. WhatsApp messaging and reminders/follow-ups are separate optional consents. Without messaging consent the patient is never messaged proactively (token SMS/WhatsApp, "your turn", reminders, recalls); the receptionist is told when a running-late notice could not be sent.
- A chat from an unknown number is a "lead": info questions are answered, but nothing is stored until they reply YES to consent. Leads are never messaged proactively.
- Running late: the doctor's text creates a pending proposal; **no message is sent and no appointment moves until the doctor confirms** (`confirm_schedule_shift` allows `staff:doctor` only, so no agent can confirm). Appointments whose shifted time would pass the end of their opening window become `needs_rebooking` and the patient is offered the next free slots. Voice notes will arrive as transcripts through the same `/staff/schedule/propose` endpoint once speech-to-text exists.
- Follow-up defaults (per clinic in `clinic_settings.followup_rules`): reminder 24h before, post-visit check-in 24h after the visit, recall after 90 days without a visit or upcoming booking (max one per 30 days). A post-visit reply that says things are not better raises an urgent item; every post-visit reply reaches the team.
- Red-flag matching errs towards escalating (e.g. any newborn + fever, "baby" + high fever). Eval run: 48 messages, all safety rules pass in offline mode.
- Conversation language is sticky once the patient writes in Devanagari; Hinglish (Roman Hindi) keeps the conversation's current language but red-flag and intent rules cover Hinglish.
